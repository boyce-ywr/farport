# Farport 0.1.23（构建 29）正式版

发布进行中：正式包构建与验收完成后，先上传为草稿，核对附件后再公开。

## 修复

- **在 Docker 容器里运行的程序输出的路径点不开**：0.1.22 中，tmux 窗格前台是 `docker exec`/`docker attach` 时（例如在容器里运行 Claude Code），Cmd+点击路径会提示"路径不属于此主机"。现在 Farport 会识别窗格里的容器，读取它的工作目录和挂载，把容器内路径换算成主机路径，再用同一套"文件"功能打开目录或预览文件。详见 [问题复盘](../issues/2026-11-09-终端路径点击在容器窗格被拒绝.md)。
  - 容器内的相对路径以 `docker exec -w` 指定的目录为基准，其次是容器的 WorkingDir；`~` 按容器用户的 HOME 展开（root 为 `/root`）。
  - 只有 bind 挂载的路径在主机上有对应位置。命名卷、tmpfs 或容器自身文件系统里的路径，会提示"只存在于容器内"。
  - 容器内外路径不同时（如把项目挂载到 `/app`），顶部会提示两者的对应关系；路径相同时不打扰。
  - 窗格里的 docker 连的是另一台机器上的守护进程时，挂载路径属于那台机器，会拒绝打开并说明原因。
  - 本机普通终端里运行 `docker exec`/`docker attach`，以及 Agent 面板里的容器终端，也按同样方式支持。
- **sudo、su 下的路径不再被拒绝**：它们和当前主机是同一个文件系统，按主机路径打开；只有前台在通过 ssh/mosh 连接其他主机时才拒绝。

功能提交：`6426e5c`（0.1.22 的终端路径点击功能见 `a79cc4d`）。

## 使用边界

- tmux 窗格处于复制模式时识别不了其中的 Docker 容器，需要先退出复制模式。
- 远端普通终端（非 tmux）拿不到前台进程，仍按主机路径查找。
- 容器内的 Agent 切换过工作目录（不再是 `-w` 指定的目录）时，相对路径仍按 `-w` 目录解析，可能找不到。
- **仍为 ad-hoc 签名，未完成 Developer ID 签名和 Apple 公证。** Intel 版只做交叉构建和静态验证，不在真机上运行验证。
