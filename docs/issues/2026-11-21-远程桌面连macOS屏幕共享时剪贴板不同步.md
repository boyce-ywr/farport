# 远程桌面连 macOS 屏幕共享时剪贴板不同步

- **影响范围**：0.1.21 起的内嵌远程桌面，远端为 macOS 自带屏幕共享（ARD/VNC）时，本机与远端之间复制粘贴双向都不生效。Linux 等第三方 VNC 服务端正常。
- **发现日期**：2026-11-21（用户反馈：Apple“屏幕共享”app 能复制粘贴，Farport 不能）
- **修复版本**：0.1.30
- **严重程度**：中（功能不可用，有 Apple 客户端可替代）

## 现象

Farport 内嵌桌面连接 mac-mini 等 macOS 主机，本机复制的文本在远端粘贴不出来，远端复制的文本也回不到本机；同一主机用 Apple“屏幕共享”app 打开则正常。

## 定位过程

1. 代码核对：Farport 实现了标准 ClientCutText/ServerCutText 与扩展剪贴板（0xC0A1E5CE，UTF-8），回归只覆盖了 Linux TigerVNC/x11vnc 夹具，从未对 macOS 服务端验证剪贴板。
2. 资料核对：多份社区报告指出 macOS 自带屏幕共享服务端对第三方客户端（TightVNC、Remmina 等）不响应标准剪贴板消息；Apple 客户端的剪贴板同步走其私有的 RFB 3.889 扩展。
3. 没有用户的 macOS 账号口令，未能抓取“服务端忽略 ClientCutText”的协议证据；结论基于资料与用户现象推断。
4. 替代路径验证：用回环 SSH 在“远端”执行 `pbcopy`/`pbpaste`，确认 SSH 会话能读写图形会话登录用户的剪贴板，含中文与换行。

## 根因

macOS 屏幕共享服务端不实现第三方客户端可用的 VNC 剪贴板同步，Farport 只依赖 VNC 协议同步剪贴板。

## 修复

`RemoteDesktopSession`：服务端为 macOS、桌面就在这台 SSH 主机上时，获得焦点经 SSH 执行 `pbcopy` 写入远端剪贴板，失去焦点经 SSH 执行 `pbpaste` 读回本机；远端命令先核对 SSH 用户与 `/dev/console` 所属用户一致，否则提示并回退 VNC 协议；固定 UTF-8 语言环境。`RemoteDesktopNSView` 在失去焦点时通知会话。其他服务端行为不变。

## 验证

- 新增 `desktop-ssh-clipboard` 检查（回环 SSH 模拟远端 Mac，中英文）：pbcopy 写入、pbpaste 读回一致，用户核对通过，桌面目标判断正确。
- `scripts/check-remote-desktop.sh` 与 `--ui`（中英文）：Linux 远端的扩展剪贴板中文双向同步等全部通过。
- 未在真实 macOS 屏幕共享会话中端到端验证（需要用户登录），请用户实际复制粘贴确认。

## 避免再犯

协议类功能要对每类主流服务端（尤其 macOS 自带屏幕共享）各做一次端到端验收；无法验收的服务端在版本说明中明确标注“未验证”。
