# 大目录导航等待无反馈

- 发现日期：2026-10-19。
- 严重程度：中；影响远程文件浏览的可感知响应，不涉及远端文件损坏。
- 影响范围：文件数量较多、目录枚举或网络往返较慢的 SFTP 目录。
- 修复提交：与本文件更新一同提交，可通过 Git 历史查询。用户运行的安装版没有被替换。

## 现象与已确认的边界

用户反馈 Android/Termux 共享存储下的相机目录点击没有反应。截图只能确认目录已选中，不能据此判断是否收到双击事件。Farport 的既有交互为单击选中、双击打开。

诊断只读取指定设备的身份和目录元数据，沿用已有 SSH 主机指纹校验；未打开照片、视频内容，未修改远端文件。地址、账号和本机诊断配置不写入公开文档。

- SSH 检查确认目录具备读取和搜索权限，包含 17,991 个直接子项。
- 原始 SFTP OPENDIR 约 0.75 秒成功；180 批 READDIR 约 15.4 秒完成，无访问拒绝。
- Farport 实际 `SFTPClient.listForBrowsing` 返回 17,991 项、跳过 0 个异常名字；修复前一次读取约 19.8 秒。
- 隔离 QA 窗口的原生鼠标事件确认：单击只选中，双击确实触发导航，并在约 17.2 秒后进入目录。未复现永久打不开，复现的是长时间停留旧目录、反馈不足。
- 同一次 QA 中，20 轮 `visibleFiles`/`selectedFiles` 读取耗时 0.594 秒，超过 0.2 秒回归阈值。

## 定位与根因

先用权限及协议探测排除访问拒绝，再用真实客户端和 NSTableView 双击事件区分远端等待与交互失效。

1. `listForBrowsing` 逐批请求完整目录；`FileModel.load` 等待全部返回，才更新路径和表格。旧界面只有工具栏小转圈，不显示目标目录或已读取条目，容易被误认为点击无效。
2. 等待期间再次激活同一目录，会取消当前枚举并重新开始。用户反复双击会延长等待。这是旧调用链确认的机制，不代表已观测到用户实际反复双击。
3. `visibleFiles` 原先每次读取都过滤并自然排序。表格、数量统计和选中项查询反复调用它，在主线程增加额外开销。

大目录读取耗时不是排序修复能全部消除的：本次不改 SFTP 批量协议、不隐式截断结果、不把部分列表作为完整目录交给传输或删除。

## 最小修复

- `SFTPClient.listForBrowsing` 增加可选的条目计数回调；不改变完整目录结果、异常名字处理和严格递归接口。
- `FileModel` 维护目标目录与条目进度，同一目标仍在读取时不重启请求；取消、错误、完成或切换请求后拒绝过期进度回写。
- `FileWorkspace` 显示目标路径、已读取项数和取消按钮；成功前保留旧目录，避免文件操作目标与显示内容不一致。
- 缓存过滤、排序后的列表；文件、筛选条件、隐藏项、排序或界面语言变化时失效。空选择直接返回空数组，避免扫描整个目录。
- 增加中英文加载文案和真实设备只读回归入口。

## 验证

```bash
bash scripts/check-large-directory.sh <地址> <端口> <用户名> <大目录>
bash scripts/check-directory-navigation.sh
FARPORT_LANGUAGE=en .build/debug/workbench-tests --english-check
```

真实设备回归覆盖：原生单击/双击、目标路径和进度、重复激活不重启、完整条目数与表格行数一致、取消后旧回调不回写、缓存失效以及中英文切换。首轮修复后重复视图读取降至 0.078 秒；加入空选择快速路径后，同一检查小于 1 毫秒。最后一轮真实双击到显示 17,991 项耗时 12.224 秒；目录枚举受网络和设备状态影响，不把单次耗时变化归因于缓存修复，也不宣称秒开。

普通 SSH 目录导航与五列原生表头 15 次点击（升序/降序/默认）均通过，设备检查加核心回归为 2,112 项断言通过。验证使用独立工作区，没有重启或覆盖用户正在使用的应用。

QA 在修复前后都出现 NSTableView 重入警告，但导航和表头断言通过；本次不扩展修改原生表格实现。独立临时 Swift 探针在执行前收到 SIGKILL，重新签名后仍一样；改用现有 SwiftPM 测试与应用目标完成实际验证，未将该启动限制当作远端访问失败。

## 避免再犯

慢目录导航必须提供目标和进度，重复激活同一目标不能丢弃已有工作；性能回归需使用万级条目，并同时验证列表派生状态的缓存失效，而非只覆盖小目录或只确认没有抛错。
