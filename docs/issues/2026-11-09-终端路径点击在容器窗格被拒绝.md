# 终端路径 Cmd+点击在容器窗格中被拒绝

- 影响范围：0.1.22。tmux 窗格前台是 `docker exec`/`docker attach`（如远端 Mac 上 tmux 中运行 docker-claude 里的 Claude Code）时，Cmd+点击任何路径都失败。普通 Shell 窗格不受影响。
- 发现日期：2026-11-09，0.1.22 发布后由用户在主场景中发现。
- 修复 commit：`6426e5c`，随 0.1.23 发布。
- 严重程度：中。新功能在用户最主要的使用场景（容器内 Agent）里完全不可用，但不影响已有功能和数据。

## 现象

点击后弹出"tmux 窗格正在运行 SSH、容器或其他用户环境，路径不属于此主机，未打开。"

## 定位过程

0.1.22 的设计里，窗格前台命令只要属于 `ssh/mosh/docker/podman/su/sudo` 中的一个，就一律拒绝。理由是这些情况下路径可能不属于当前主机。端到端检查只覆盖了普通 Shell 窗格，没有覆盖容器窗格，所以没有暴露出来。

在用户的环境里核实了以下事实：
- docker-claude 以 `docker exec -it -w <项目目录> docker-claude …` 启动，容器挂载了 `/Users -> /Users`，容器内外路径相同，主机的文件功能（SFTP）完全可以打开。
- 容器的 `/root` 是 Docker 命名卷，主机文件系统上看不到。
- Farport 的附件功能已经能识别窗格中的 docker 进程和目标容器，但不读取挂载信息，`-w` 参数解析后也丢弃了。

## 根因

把"路径可能不属于当前主机"简化成了按前台命令一刀切拒绝，没有利用已经具备的容器识别能力，去判断容器路径能否对应到主机路径。

## 修复

- 前台是 docker 时，复用附件的容器识别，用原窗格的 docker 客户端和 context 读取容器的 WorkingDir、User、Mounts。挂载信息按 docker 客户端进程身份缓存。
- 容器内路径以 `docker exec -w`、WorkingDir 为相对路径基准，`~` 按容器用户 HOME 展开（root 为 `/root`）。按最长挂载目标前缀换算：bind 挂载换算成主机路径，用同一套文件功能打开；命名卷、tmpfs 或未挂载路径提示"只存在于容器内"。
- 远端窗格的 docker 守护进程不是本主机的 unix socket 时拒绝，因为挂载源属于另一台机器。
- `sudo/su` 不再拒绝（同一文件系统），只有 `ssh/mosh` 仍拒绝。Agent 面板的容器终端也按相同方式支持。
- 容器路径与主机路径不同时，在顶部提示换算关系。

## 验证

- 单元断言：挂载换算（同路径、不同路径、挂载点本身、按路径段匹配、命名卷覆盖 bind、`..` 规范化、根目录挂载）、容器 HOME、`-w` 各种写法和真实 docker-claude 启动参数。
- 端到端：本机 tmux 和回环 SSH（模拟远端 Mac）的 tmux 中执行 `docker exec -it -w /app`，中英文各一轮，覆盖不同路径挂载的相对路径预览和换算提示、同路径挂载目录进文件页、命名卷提示、不存在路径提示；原有本机和隔离 SSH 场景同时回归。

## 测试中踩到的坑

最初在容器里直接敲带长绝对路径的 `clear; printf …`，命令回显超过一行发生换行；`clear` 之后行缓冲残留了换行标记，SwiftTerm 的隐式链接识别把相邻两行拼成了 `/root/vol/a.mdCBAD docs/missing.`。改为把输出写进脚本，只敲短命令，就不再出现。真实使用中如果遇到类似的跨行误拼，可以参考这条记录。

## 避免再犯

- 新功能的端到端检查必须覆盖用户主场景：SSH → tmux → docker 容器内 Agent（见 memory 中的远端验证方法）。
- 判断"不属于当前主机"时，优先利用已有的识别能力细分情况，不要按命令名一刀切拒绝。
