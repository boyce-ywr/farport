# 打包签名与启动验收

- 发现日期：2026-10-13。
- 影响：本地 `.app` 打包及图形验收。
- 严重程度：阻塞交付验收，不涉及生产数据。
- 修复 commit：未提交。

## 已定位并修复的打包问题

1. SwiftPM 生成的资源访问器把资源查找路径指向 `.app` 根目录，初版打包据此放置资源，`codesign` 报 `unsealed contents present in the bundle root`。
2. 核查锁定版本 SwiftTerm 的实际资源查找实现后确认：该组件专门支持 `Contents/Resources`，无需修改第三方源码。资源改到标准位置后，严格签名验证通过。
3. 上游 LICENSE 是只读文件。直接复制后再次构建无法覆盖。改用 `install -m 644`，保持原始内容并保证本项目输出可重复生成。
4. 可执行文件经临时文件加原子替换写入，避免原地覆盖运行文件。

## 后续缩小的运行阻塞

签名严格验证通过后，进程仍以 137 退出。本机日志包括 `AppleMobileFileIntegrityError Code=-423`（ad-hoc 或未知证书链），以及公司 EDR 对该进程的标签。未找到足以唯一归责某一组件的终止事件，因此不将猜测写成已确认根因。

对主可执行文件进行相同内容与签名的原子替换，前后 SHA-256 一致，仍不能正常运行。该实验排除了简单依靠重写同一二进制解决的路径；没有通过重命名或伪造身份规避限制。

后续原生 ARM Debug 包成功运行并完成真实 SSH 截图；ARM Release 独立程序也完成真实界面验证。用户命名后的应用身份仍为 `local.sshworkbench.mac`，没有伪造身份绕过限制。

但最终 Universal 包在用户 Applications 目录启动依然失败。2026-10-13 14:19 对失败进程采样，显示 ARM64、物理 footprint 96 KiB、主线程全部采样位于 `_dyld_start + 0`，未进入 Swift/应用逻辑。直接执行和 LaunchServices 启动都未生成验收截图。原始采样保存在忽略版本控制的 `.test/release-launch-sample.txt`。

日志中的 ad-hoc 提示与 EDR 普通标签也曾出现在成功运行的 Debug 包，不能仅凭这些日志把终止归责 EDR。下一步应收集用户正常打开安装包时的系统提示，必要时使用合法的签名、公证或 IT 授权流程。尚未完成这一项前，不能把开发版本成功运行表述为发行包已经可用。
