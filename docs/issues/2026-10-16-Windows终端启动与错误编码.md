# Windows 终端启动与错误编码

- 日期：2026-10-16；版本：0.1.8（10）。
- 严重程度：高。Windows 原生终端在启动前即失败，tmux 页错误不可读。
- 修复提交：见本文件首次引入的 Git 历史。

## 现象与定位

用户 Windows 主机启动终端显示带 `true` 的乱码，tmux 页显示无法识别的字符。初次只读连接在 SSH 用户认证阶段被重置；稍后连接恢复，记录到 OpenSSH for Windows 9.5，默认 Shell 为 CMD，系统编码为 CP936。

相同主机执行 `true` 返回退出码 1，原始错误按 GB18030/CP936 解码为“不是内部或外部命令”。执行 POSIX Shell 路径也返回“系统找不到指定的路径”。这与截图相符，并非密码错误或终端字体问题。

## 修复

- 连接测试和终端启动共用 ASCII `echo` 探测，不再依赖 POSIX 的 `true`。普通交互会话仍打开远端默认 Shell，不改注册表或用户配置。
- 进程诊断信息依次识别 UTF-16 BOM、UTF-8、GB18030；无法识别时给出明确提示。只处理 stderr，标准输出仍是原始字节，避免影响 SFTP、文件或其他二进制数据。
- tmux 管理先检查 POSIX Shell 能力；若识别为 Windows 原生 Shell，显示“使用普通终端或连接已配置的 Linux/WSL SSH 服务”的说明，不继续投递 POSIX tmux 脚本。结果在当前传输对象内按连接配置缓存。

## 验证

- Windows 真机只读检查：连接测试、SFTP、原生交互终端实际执行 ASCII 命令与中文 echo，输出行均由终端缓冲区断言，不用输入命令自身的回显代替结果。
- 原始 CP936 错误通过解码断言；tmux 能力提示与本地化文案一致，没有乱码。
- 核心测试覆盖 CP936、UTF-8、UTF-16 BOM、跨平台连接探测和标准输出字节保真；隔离 Linux SSH/tmux 回归检查原有路径。
- GUI 检查入口 `SWB_QA_SCREEN=windows-ssh` 还要求独立的单主机配置和 `SWB_QA_WINDOWS_READONLY=1`。真实地址及截图只存 `.test/windows-*`。

本轮不声称 Windows 附件上传、监控或所有 Windows Shell 变体均通过验收；没有切换默认 Shell、安装组件、修改 SSH 或 tmux 配置。
