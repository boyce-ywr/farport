## 发布决策

**首次尝试时停止正式发布。** 2026-10-28 首次查验的最新已发布版本为 0.1.17，非草稿、非预发布。不能把先前独立源码构建的成功结果或临时验证应用直接改名为正式包，也不能声称安装、签名、三架构和在线更新验收已完成。用户随后要求继续修复至发布完成，后续状态记录在文末与版本说明中。

## 现象与环境

- `xcode-select -p` 指向 `/Library/Developer/CommandLineTools`；当前没有可用的完整 Xcode 安装。
- Swift 为 Apple Swift 6.4，CLT 包版本 `27.0.0.0.1788430756`；系统报告 macOS 27.0.1。
- `swift build --build-system native --product SSHWorkbench -vv` 在 SwiftTerm 构建插件阶段返回：

```text
error: build planning stopped due to build-tool plugin failures
```

插件能够完成编译和链接，但没有执行到更新其工作目录中的触发文件。工具输出没有提供更具体的插件异常。

## 最小复现与定位

在忽略目录下创建不引用 Farport 或 SwiftTerm 的极小 Swift 包：一个输出固定文本的可执行目标，附带一个 `BuildToolPlugin`，其 `createBuildCommands` 只返回空数组。该包使用同一 native 构建器仍出现完全相同的插件错误。

由此确认问题不需要业务源码、SSH、Docker 或 SwiftTerm 生成器即可触发。故障边界位于当前工具链/系统执行环境的插件宿主路径，**还不能确定是 SwiftPM、CLT 运行库、系统启动约束中的哪一层**。

额外有界诊断：

1. 详细日志和此前全新 scratch 目录均复现，非单纯旧工程缓存。
2. 单次关闭 SwiftPM 子进程沙箱的诊断未使构建通过，不能把该选项当成解决方案；未修改系统防护配置。
3. 直接运行生成的插件和一个加载 `libPackagePlugin.dylib` 的独立程序出现等待；采样只看到 `_dyld_start`，不足以定位具体根因。
4. 对仅用于诊断的本地可执行文件，使用与 SwiftPM 已生成的 Debug 工具相同的 `get-task-allow` 调试签名后，直接执行可以退出，加载运行库的程序可以完成。
5. 但使用固定环境、保留该签名再次通过 SwiftPM 调度插件仍失败，包含开启和关闭插件沙箱的两种情况。**直接执行恢复不等于插件构建恢复**，不能把签名差异写成已修复根因。

所有诊断命令均有超时；没有关闭系统安全策略、修改 CLT 或第三方源码，也没有对发行应用添加调试权限。

## 后续定位与构建修复

继续排查时，官方 Swift 6.4.1 安装包经签名和 Apple 公证校验后，提取到项目隔离目录用于对照，没有替换系统 CLT。它仍复现相同的插件错误；清洁环境和 GUI 登录上下文也未解决。

对单独的诊断版 SwiftPM 使用 LLDB，在插件异常抛出点读到确切错误 `invocationEndedBySignal(signal: 9)`。系统 AMFI 日志同时记录该临时插件因 ad-hoc 或未知证书链而拒绝运行。开发签名在最小例子上曾通过，但在完整项目中不稳定，不能把它视为可靠发布修复；相关诊断只针对本地工具，没有关闭系统安全机制或给发行应用增加调试权限。

最终采用明确、可复现的生成步骤，不再依赖插件宿主：

1. `scripts/prepare-swiftterm.sh` 锁定原依赖 1.20.0 的精确提交，在 `.build/swiftterm-source` 保留干净 detached checkout，并通过 `git archive` 导出库源码到 `.build/swiftterm`。
2. 直接通过系统 Swift 解释执行上游未修改的 `BuildInfoGenerator.swift`，输出 `SwiftTermBuildInfo.swift`，避免再产生需要单独启动的临时插件。与旧上游插件生成结果逐字节一致。
3. 版本化保存的 `BuildSupport/SwiftTerm/Package.swift` 描述同一个库目标、Metal 资源、部署平台和语言模式；仓库根 `Package.swift` 正式依赖该准备结果，不使用临时测试包。
4. 打包前由 `scripts/check-swiftterm-source.py` 核对所有库文件和许可证的精确 Git blob、生成文件集合、构建描述及原生成器输出；发现修改即停止。
5. 系统 CLT 的根目录常规 `swift build --build-system native` 已恢复通过。三架构正式包与运行验收以本轮发行记录为准。

没有降级 SwiftTerm、改写其运行时代码、关闭系统防护或跳过正式包验收。官方对照工具链与诊断文件均留在忽略目录；正式构建使用当前系统 CLT。
