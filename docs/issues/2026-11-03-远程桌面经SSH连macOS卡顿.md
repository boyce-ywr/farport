# 远程桌面经 SSH 连 macOS 卡顿、拖影，“流畅”档无效

- 影响范围：远程桌面第 1 期预览（`1b905eb`）；远端为 macOS 屏幕共享，链路带宽较低时（实测公司 Wi-Fi 互访）
- 发现日期：2026-11-03（用户反馈：经 SSH 远程访问比系统屏幕共享慢得多，切到“流畅”也一样卡）
- 修复 commit：待提交（第二轮的拖影修复与第一轮一起提交）
- 严重程度：高（远端为 Mac 时基本不可用）

## 现象

状态栏显示：1920×1080，编码 ZRLE，384 KB/s，延迟约 2707 ms；画面严重滞后，切换到“流畅”档没有变化。

## 定位过程

1. 先排除 Debug 编译：用户用的就是 Release 预览包。
2. 第一次测量时，ssh 通道几乎没有流量，Farport 和 `screensharingd` 的 CPU 都接近 0。原因是 mac-mini 显示器已经休眠、画面不变，**这次测量无效**。之后测量前都先用 `caffeinate -u` 唤醒屏幕，并用本地动画页面制造稳定负载。
3. 用临时测量入口（无界面 RFBClient，经 `ssh -W` 连真实 macOS，口令从 600 权限文件读取，测完删除）对比编码：
   - 请求 ZRLE：4.6 fps，0.84 MB/s；
   - 请求 Hextile：服务端退回 **Raw**，1.0 fps，1.28 MB/s；
   - 说明 macOS 服务端对第三方客户端只提供 ZRLE/Raw，不支持 Tight（JPEG），也不支持 Hextile。
4. Raw 几乎不耗服务端 CPU，流量却只有约 1.3 MB/s，于是怀疑链路本身。实测结果：这台 Mac 到 mac-mini 走 SSH 传 30 MB 用时 31 s（约 1 MB/s），裸 TCP 为 1.78 MB/s；ping 平均 107 ms，最高 199 ms。两台机器都使用 Wi-Fi（公司无线网络互访）。
5. 对比色深（都用 ZRLE）：32 位 1.9 fps、每帧 466 ms；**16 位 6.1 fps、每帧 48 ms**；8 位会被 macOS 服务端直接断开。
6. 加深流水线（在途请求 2 个、3 个）反而更慢（6.2 → 5.0 → 3.4 fps），保持单请求流水线。
7. 按画质档复测两轮：无损（32 位）3.5 fps、0.8 MB/s、每帧 170–230 ms；均衡/流畅（16 位）6.1–6.8 fps、0.2–0.35 MB/s、每帧 15–42 ms。“流畅”曾有一次测得 3.1 fps，复测与“均衡”一致，属于测量波动。

## 根因

- macOS 屏幕共享对标准 RFB 客户端只提供无损的 ZRLE/Raw。Farport 的画质档位只调 Tight 的 JPEG 质量和压缩级别，对 macOS 远端完全无效。
- 32 位色 1080p 的 ZRLE 数据量超过低带宽链路的承载能力，画面更新积压，延迟达到秒级。系统屏幕共享使用 Apple 私有的有损自适应编码，所以没有这个问题。

## 修复

- `RFBDecoders`：支持 16 位色（RGB565）线路像素，Raw、Hextile、ZRLE、光标伪编码都按字节数解析，用 65536 项查找表转换为帧缓冲像素。
- `RFBQuality.pixelDepth(macOS:)`：远端为 macOS 时，“均衡/流畅”用 16 位色，“清晰（无损）”保持 32 位色；其他远端保持 32 位色 + Tight JPEG。低色深时不请求 Tight。
- 像素格式只在连接时确定（RFB 无法安全地中途切换：流水线下新旧格式的更新无法区分，macOS 也不支持 Fence）。`setQuality` 在需要换色深时返回 false，会话层提示后自动重连（有保存的口令时无感知）。

## 验证

- 真实 mac-mini 经 SSH：均衡/流畅档帧率约为无损档的 2 倍，每帧接收解码耗时降到 1/4–1/10，延迟由秒级降到数百毫秒。16 位色截图颜色正确，仅渐变处有轻微色带。
- 新增夹具回归：16 位色 Raw/Hextile/ZRLE 与 32 位基准比对，最大通道误差为 5（容差 8）；画质到色深的映射断言。
- 核心 2848 项、协议 24 项、界面中英文两轮全部通过。

## 第二轮：拖影（2026-11-04）

16 位色上线后，用户仍反馈“比系统屏幕共享慢很多”。同条件实测时，Farport 状态栏显示 28–36 fps、延迟 11–15 ms，数字上并不慢，但动画方块后面拖着多个不同时刻的残影。

### 定位

1. 排除显示层：IOSurface 双缓冲会为每块缓冲累计各自的脏区域；而测量程序直接读帧缓冲，同样有残影。说明问题出在收到的数据。
2. 量化指标：测试页改为纯品红 300×200 实心方块（mac-mini 为 1 倍缩放，单帧约 60000 像素）。每 0.5 秒统计一次帧缓冲中的品红像素：中位数 21–22 万，最大 29 万。截图中有一块 182×200 的品红区域在多张截图里位置完全不变。
3. 排除流水线：流水线与非流水线各测两轮，残影程度相同。
4. 决定性实验：残影出现后发一次整屏非增量请求，品红像素从 279002 降到 56958。说明那些区域的最新内容，服务端从未在增量更新中发送过。

### 根因

macOS 屏幕共享对标准 RFB 客户端的增量更新会漏报部分变化区域（推测与 GPU 合成图层的脏区域检测有关，未证实）。漏报的区域停留在旧内容上，直到再次有变化覆盖它。系统屏幕共享走私有的视频流式编码，不依赖逐区域的脏区域上报，所以没有这个问题。

### 修复

- `RFBClient`：仅对 macOS 远端，累计增量更新的变化区域；该区域安静 0.2 秒或持续变化超过 0.5 秒后，补发一次该区域的非增量请求。补发的响应与请求区域完全相同，据此识别并不再计入变化区域，避免自我循环。没有选择定时整屏刷新：壁纸是照片，一次整屏无损数据就有 MB 级。
- 实测：两轮品红像素中位数都恰好 60000，整屏刷新前后一致；流量由约 0.3 MB/s 升到约 0.8 MB/s（当时链路约 1.9 MB/s）；帧率不变。

### 附带修复：钥匙串授权框卡死界面

每次重新打包，ad-hoc 签名都会变化，读取已保存口令时系统会弹出钥匙串授权框。原先读取放在主线程，授权框弹出期间整个界面冻结，状态栏时钟停止走动。采样到主线程阻塞在 `SecItemCopyMatching`。现在改为在 RFB 线程读取钥匙串，主线程只负责弹出登录框。

## 避免再犯

- 测远端画面性能之前，先确认远端屏幕处于唤醒状态（`caffeinate -u`），并使用固定的动画负载；无流量时先怀疑“画面根本没变”。
- 评估编码时，先确认服务端实际选了哪种编码：请求 Hextile 时 macOS 会悄悄退回 Raw。
- 遇到“带宽很低”的现象，先用 SSH 和裸 TCP 测链路基线，再怀疑协议实现。
- 不要从 SSH 会话里用 osascript 控制远端 App：会在远端弹出自动化授权框，命令会一直卡住等待。
- 判断画面是否正确，要用可量化的测试图案（纯色方块的像素数），不能只看 fps 和延迟。
- 依赖服务端脏区域上报的增量协议，要准备好“补刷新”兜底；判断标准是整屏刷新前后画面是否一致。
- 自动化操作桌面前，先确认屏幕没有锁定（前台不是 `loginwindow`），否则按键可能落到锁屏界面上。
