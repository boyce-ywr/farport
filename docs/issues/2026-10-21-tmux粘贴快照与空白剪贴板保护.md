# tmux 粘贴快照与空白剪贴板保护

- 发现日期：2026-10-21。
- 影响范围：0.1.14 的终端文本粘贴及 OSC 52 剪贴板写入；用户报告在 tmux 内用 `Ctrl+B`、`C` 新建窗口后容易出现。
- 严重程度：高；已有剪贴板内容可能被空白替换，实际粘贴内容可能与用户确认的文本不同。
- 修复 commit：包含本文的提交，可用 `git log -1 --format=%H -- docs/issues/2026-10-21-tmux粘贴快照与空白剪贴板保护.md` 查询。
- 发布状态：源码修复与隔离验收，不替换已发布的 0.1.14 安装包，也不自动修改用户设置或正在运行的应用。

## 现象

用户已开启“始终允许终端写入剪贴板”和文本读取，仍看到“粘贴多行内容？”；确认后未插入原内容，反而显示复制反馈，剪贴板变为空白。

原有两个设置只控制 OSC 52 协议读写，不控制多行文本粘贴确认。此前多行确认没有独立开关；这解释了弹框，但不能把内容丢失解释为用户配置问题。

## 定位与可复现证据

使用独立 tmux socket、空配置和原始 PTY 接收程序，不接入用户真实会话。通过终端发送 `Ctrl+B`、`C` 创建新窗口，再派发 `⌘V` 并点击真实 `NSAlert` 按钮。仅使用测试文本，测试结束恢复剪贴板和偏好。

1. 普通新窗口中的多行确认、逐字节接收与剪贴板保持，在修改前已经通过。因此不能认定“新建窗口本身必定触发复制”。
2. 在同一隔离 tmux 中执行 `set-buffer -w`，让 tmux 向客户端发送仅换行的 OSC 52 写入。修改前出现：`FAIL · 真实tmux空白OSC52清空剪贴板：length=1，message=已复制到 Mac 剪贴板`。剪贴板并非字节长度为零，而是被替换成看起来空白的换行。
3. 在多行确认框打开期间，用测试夹具更改系统剪贴板，再确认粘贴。修改前出现：`FAIL · tmux新窗口粘贴字节不符：actual=36, expected=40`。接收端收到的是变化后的文本，而不是确认框展示的原文本。
4. 另行进入 tmux 复制模式时，终端文本粘贴也可被 tmux 消费而不进入窗格程序。本次未自动退出复制模式或改写 tmux 配置，不能把这一模式差异称为已修复。

用户现场的完整时序尚未捕获，不能证明每次报告都由上述两个缺陷共同触发；它们是分别通过真实 tmux 和 PTY 证实的缺陷。

## 根因

### 仅空白的协议写入被视为有效复制

`TerminalClipboardState.receive` 原来只检查 `!text.isEmpty`。换行、空格和制表符都可通过，随后清空原剪贴板并写入空白，而且显示复制成功。始终允许写入会省去授权提示，使覆盖直接发生。

### 确认展示与实际发送不是同一份数据

`SafeTerminalView.paste` 先读取文本展示确认，确认后调用父类 `paste`；父类再次读取全局剪贴板。模态对话框期间发生的剪贴板变化，因此可能替换实际发送的内容。

## 修复

- 拒绝仅含空白的 OSC 52 写入，并清理其待处理内容；不清空已有剪贴板。有效文本保留原来的首尾空白，手动本地选区复制不受影响。
- 文本粘贴只读取一次快照，确认后直接发送该快照，保留终端的 bracketed paste 标记，不将粘贴文本转换成增强键盘事件。
- 取消不发送；等待确认期间 PTY 已结束或进程已替换时不向新进程发送。
- 新增“设置 → 隐私与安全 → 粘贴多行文本前确认”，默认开启，独立持久化并立即生效。关闭可能直接执行文本中的命令，界面明确提示风险。
- 图片与文件仍优先进入原附件处理流程；不放宽附件确认、OSC 52 前后台隔离和读取权限。

## 避免再犯

- 剪贴板是可被其他进程或异步协议事件改变的全局状态；确认与执行必须使用同一份快照，不应在确认后重新读取。
- 协议“非空”检查必须考虑视觉空白，不能仅用字符串长度判断复制是否有内容。
- 终端权限、用户主动粘贴的确认以及 tmux 输入模式应分别验证，避免把授权开关当作所有输入行为的总开关。
- 回归要校验接收端实际字节和剪贴板 change count，而不是只看弹框是否关闭或界面是否显示成功。
