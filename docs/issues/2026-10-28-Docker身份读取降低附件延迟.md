# Docker 身份读取的额外进程成本与附件延迟

- 发现日期：2026-10-28。
- 影响范围：Farport 本机 tmux 的 Docker 附件链路；普通本机、SSH 文件上传路径未改。
- 严重程度：交互性能问题；不涉及放宽读取权限或目标校验。
- 修复 commit：`e83923a`；独立源码构建与最终验收通过，未发布安装包。
- 前置修复：`bd2b57d`，已将同一小图复用容器绑定的插入耗时从约 18 秒降到约 7 秒，见 [前次复盘](2026-10-28-tmux鼠标松开复制与Docker附件延迟.md)。

## 定位

剩余延迟的候选是 Docker CLI 启动、重复 tmux/容器检查、插入前串行等待。本轮先测命令成本：

- `docker info --format '{{.ID}}'` 热运行约 0.53–0.54 秒。
- 同一个已授权本机 Unix socket 的 `GET /info` 热运行约 0.03 秒，返回相同 daemon ID。
- 每次上传和插入前都会多次检查该身份；串行重复放大了 CLI 路径开销。没有进一步归因 Docker CLI 内部的哪一步耗时，也没有把接口耗时当成整个图片发送耗时。

## 修改

- 新增 `DockerEngineIdentity`，首次通过 `/version` 获取版本，严格验证版本仅含两段 ASCII 数字，再通过版本化 `/info` 读取 ID；后续复用版本，但**每次重新读取身份，不缓存 ID**。
- 仅使用已经过 `DockerUnixEndpoint` 校验的本机 Unix socket。系统 `curl` 禁用个人配置和代理，不跟随重定向，限制连接/总耗时和响应大小；只有 HTTP 200、有效 JSON 和非空合法字段可以通过。
- 出错、权限不足、非法 JSON、超限、取消、版本不兼容均失败，不静默回退成“已验证”。错误不包含原始响应正文。
- Docker context、socket、容器 ID、启动状态、原进程和用户检查仍在原有位置；上传、文件哈希与目录成员校验、最终插入仍使用既有执行链。没有删掉检查、跳过内容复核、压缩图片或降低画质。

接口依据为 Docker 官方 Engine API 文档：首次读取服务版本，再请求支持的版本化接口；本轮在当前实际 daemon 上核对 ID 与旧 CLI 路径相等。

- `ui-before.log`、`ui-after.log`：同工具链界面对照。
- `identity-check.log`、`core.log`、`english.log`、`docker-safety.log`：身份及安全回归。
