# Shift 拖选无法取消、再次选择沿用旧起点；本机 Docker 确认目标慢

- 影响范围：Farport 0.1.19；终端程序开启鼠标上报（tmux、Claude Code 等）时的 Shift 本地选区；本机 tmux 中 Docker 附件的“正在确认目标”阶段
- 发现日期：2026-10-29（0.1.19 发布后用户反馈）
- 修复 commit：`de841d6`（发布于 0.1.20）
- 严重程度：中（选区无法取消影响正常使用；附件可用但等待明显）

## 现象

1. Shift 拖选后，单击无法取消选区；下一次 Shift 拖选从上一次的起点开始。
2. 粘贴图片时长时间停在“正在确认目标…”。

## 根因

1. 鼠标上报开启时，普通单击直接发给终端程序，不经过 SwiftTerm 的选区处理，本地选区一直保留。0.1.18 之前，选区会被新输出“意外”清除，掩盖了这个问题；0.1.19 修复“输出清除选区”后，问题暴露出来。另外，SwiftTerm 把 Shift+点击当作扩展已有选区，所以新的 Shift 拖选沿用旧起点。0.1.19 的回归只测了单次拖选，没覆盖“取消”和“再次选择”。
2. 准备阶段调用了 8–9 次 docker CLI，每次 0.1–0.37 秒：`context show`/`context inspect`（只是读本地配置）、为选择框列出全部容器的 `ps` 与批量 inspect（已不再弹选择框）、`confirm` 重复校验 daemon、每次 inspect 都启动 CLI。

## 修复

- `SafeTerminalView.mouseDown`：按下 Shift 时先清除旧选区，从点击处重新开始；鼠标上报开启时，普通单击先清除本地选区，再把点击发给程序。
- `DockerAttachmentDaemon.nativeContext`：按 Docker CLI 的优先级（--context > DOCKER_HOST > DOCKER_CONTEXT > config.json）直接读取 context 元数据，读不到时回退 CLI；发现阶段只 inspect 原窗格容器；刚完成发现时 `confirm` 不再重复校验 daemon；本机 inspect 改用已有的 socket API 客户端，引用含非常规字符时回退 CLI。

## 验证

- 新增断言：再次 Shift 拖选从新起点开始；鼠标上报开启时单击会取消选区，且点击仍送达程序。修复前失败（“再次Shift拖选没有从新的点击处开始”），修复后通过。
- “确认目标”：本机首次由 3.2 秒降到 1.4 秒，已绑定 0.6 秒；本机“摄取到插入”首次由 5.6 秒降到约 3.5 秒。远端约 4.6–5.0 / 3.3–3.5 秒。
- Docker context、DOCKER_HOST、显式 --host 三种入口安全回归，以及核心 2838 项、英文 1084 条、附件、Docker 模型、tmux 复制（含 SSH）、终端剪贴板（中英文）全部通过。
- 远端测试有一次因测试期间应用失去前台焦点而超时（active=false），重跑中英文均通过。

## 避免再犯

- 修复选区类问题时，必须同时测试“建立、保持、取消、再次建立”这几个环节。
