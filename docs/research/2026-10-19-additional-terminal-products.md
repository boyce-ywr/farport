# 补充终端产品研究：Wave Terminal 与 WindTerm 的四个个人 SSH 工作流

核验日期：2026-10-19（北京时间）。研究对象仅为 Wave Terminal 与 WindTerm。

## 口径与结论

- 面向一个人经常连接多台 SSH 主机的工作方式，选取 **4 个具体流程**；不涉及云同步、团队协作或 AI，不声称这些流程的市场使用频率，也不比较“最新版本”。
- **官方事实**来自产品官方文档或官方源码仓库；**Farport 现状**来自本次源码检查；**建议与优先级**是产品判断，不是已经实现或经过用户研究验证的结论。
- 官方资料经指定代理访问；`web.run` 未提供可用正文，因此以 `curl` 实际取得的官方内容为证据，并保留可复核的 URL，不使用无法验证的搜索引用编号。
- Farport 已有终端分栏、文件预览与 tmux 支持；本次考虑的是把已有能力串成更短的操作流程，不是重新建设这些基础功能。[F1]

## 1. Wave：在同一现场看终端输出与远端文件

**个人场景**：SSH 排查服务问题时，一侧持续看终端输出，另一侧查看配置、目录或日志文件；从文件所在目录新开终端，避免反复切页面和重新输入路径。

**官方事实**：Wave 的 widgets 可在同一标签中并置、移动和调整尺寸；Preview widget 支持目录与文件预览，目录项提供在当前目录或子目录打开新 Terminal widget 的操作，Codeedit 支持编辑并保存文件。这些是文档明确列出的操作，不据此推断“所有终端的 `cd` 都会自动同步文件面板”。[W1]

**条件与限制**：Wave 远端文件能力依赖安装在远端 `~/.waveterm/bin/wsh` 的辅助程序；普通 SSH 终端连接可以不依赖这些增强功能。不能把这种文件体验写成“仅有标准 SSH 即完整可用”，也不代表 Farport 必须照搬远端安装方式。[W3]

**Farport 适用性 / 建议 A**：现有工作台在终端与文件页面之间切换，终端布局节点只有终端与分栏。[F2][F3] 可优先验证“文件区与当前主机终端并排”和“从目录打开终端”这两个连接点，复用已有文件能力；不要扩大成通用任意组件布局系统。

**建议验收（未执行）**：同一主机的终端与文件路径可同时辨认；从含空格的目录打开终端能正确落到目标目录；切换主机不把文件操作发给另一主机；原有预览与上传流程不退化。

## 2. Wave：用命名工作区回到一组固定任务

**个人场景**：把“应用服务排查”和“个人开发机”分别保存成工作现场，下次打开时不必重新找主机、布置窗口和辨认用途。

**官方事实**：Wave 文档区分保存与未保存的工作区，保存工作区可设置名称、图标和颜色，并自动持久化标签、布局与终端历史；切换到已在其他窗口打开的工作区时，会聚焦那个窗口。未保存工作区关闭时会删除其标签，但最后一个窗口有下次启动恢复的例外。关闭窗口还会丢失尚未保存的编辑内容，因此不能将工作区保存理解为“所有状态都被保留”，更不能由此推断远端进程保活。[W2]

**Farport 适用性 / 建议 B**：本次检查到的 `Workspace` 持有内存中的会话数组与终端布局；另有主机级 `lastSession` 落盘，二者不是同一个概念。本次检查未定位到命名、保存整组工作区的入口，不把这一有限检查扩大成“全产品绝无该能力”。[F4][F5] 如果先验证了流程 1，再考虑本地保存工作区名称、主机标识与布局；保存工作区不应自动执行用户命令或存入新的凭证副本。

**建议验收（未执行）**：退出再启动可识别并恢复选定工作区；保存、删除和临时工作区含义清楚；主机配置已经删除时提示缺失；显示布局恢复不被宣传为远端进程恢复。

## 3. WindTerm：把重复输入的命令变成可辨认的入口

**个人场景**：每天查看同一组服务状态、磁盘占用或日志，不必从历史记录中反复找命令，也不必依赖一份另开的文本备忘录。

**官方事实**：WindTerm 的 QuickBar 是可自定义的按钮行，命令可以配置显示标签、发送文本和图标，并按组展示。官方文档还说明发送文本可以包含控制字符，因此它并非只展示静态笔记。[D1]

**条件与限制**：该页面发布于 2020-08-22，页面标注更新于 2021-04-23；这里引用的是仍可访问的官方功能说明，不代表本轮已在某个发行包上复现，也不推断它有参数模板、危险命令审核或按主机隔离等能力。[D1]

**Farport 适用性 / 建议 A**：本次代码检查未定位到 QuickBar 类的可保存命令入口。可从少量本地命令片段开始，显示目标主机和命令全文，默认填入后由用户确认发送；不必同时建设宏语言、自动化脚本引擎或跨主机广播。这里的确认机制是对 Farport 的建议，不是 WindTerm 官方能力描述。

**建议验收（未执行）**：一组只读命令可命名、保存、再调用；切换主机后目标明确；多行文本与控制字符不会因误点而悄悄执行；片段配置不默认保存密码、令牌或真实业务敏感数据。

## 4. WindTerm：重开应用后恢复入口，需要时才连接

**个人场景**：工作结束关闭客户端，次日重新打开时还能看见上一组连接入口；只在真正查看某个会话时发起连接，而不是启动即同时连接所有机器。

**官方事实**：WindTerm 的 Restore Sessions 文档描述重启后恢复上次的会话，但仅在对应视图激活时连接目标。页面发布于 2020-01-22，页面标注更新于 2020-06-23。[D2]

**关键边界**：这些说明证明的是客户端会话入口恢复与按需连接，不能据此宣称网络中断会自动重试、远端 shell 进程一定存活，或终端输出会完整恢复。[D2；证据边界]

**Farport 适用性 / 建议 A**：现有 `connectPreferred` 在主机偏好 tmux 时进入 tmux 流程；只有保存的 `lastSession` 非空、且远端会话列表仍包含该会话时，才附着到它。`rememberSession` 将该名称写回主机设置。因此 Farport 已有一部分恢复基础，不应再把“接回已有 tmux”列成全新能力。[F5][F6]

建议把状态分成“已恢复连接入口”“正在重新连接”“已附着现有 tmux”“原会话已不存在”，再考虑恢复上次打开的标签；不要用一个“恢复成功”覆盖不同层级。该流程与流程 2 的区别是：它不要求用户命名和维护一组工作区。

**建议验收（未执行）**：客户端重开与网络切换分别测试；远端 tmux 存在与已退出两种情况有不同提示；需要认证时正常交给认证流程；不因启动恢复而无提示新建或执行远端任务。

## 建议顺序与研究限制

建议先验证 **流程 1、3、4 的小范围改进（A）**，再决定是否建设 **命名工作区（B）**：前三者分别缩短文件与终端切换、重复命令输入以及恢复入口的操作；命名工作区需要先明确“保存哪些对象、哪些对象只是重新连接”。这是依据本次源码与功能边界提出的范围控制建议，不是市场热度排名。

本轮仅做官方资料与 Farport 源码核查，未安装运行两款竞品，未完成跨主机、断网、文件保存或发行包验收；文档可访问不等于各平台、各版本行为相同。源码检查基于 Farport `28cd90d`，局部未检索到的入口不是全产品不存在的证明。以上验收项全部是后续测试建议，不是已通过的结果。
