# Mac 远程桌面：调研与首期设计方向

日期：2026-10-19。状态：用户接受推荐方向后已实现实验原型；未更改任何远端服务或账号权限，Mac 系统账户与多主机凭据隔离仍待真机验收。

实施记录见 `../工作工具首批使用说明.md`：采用系统客户端、原子绑定 loopback 的本地入口与独立 OpenSSH `-W` 字节通道。本地数据流和隔离 SSH 回归不等于 Apple 桌面认证验收。

## 结论

建议把“打开远程 Mac 桌面”作为 Farport 的候选功能，先服务已有 SSH 主机的图形操作场景：管理 Mac mini、检查 GUI 应用、处理只能在图形界面完成的设置或排错。它对远程 Mac 用户有明显价值，但本轮没有使用频次调查，不能说所有 SSH 用户都高频需要。

首期采用的设计方向：Farport 提供主机入口、网络诊断及独立 SSH 隧道，实际桌面由 macOS 自带 Screen Sharing 打开。不要第一版就把通用 VNC、Apple Account 协助、高性能流媒体、内嵌渲染和远程管理全部混成一个功能。接受方向不代表已经实现或通过真机验收。

## 认证不是一件事

| 需求 | 含义 | 首期建议 |
| --- | --- | --- |
| 远端 Mac 用户名与密码 | 目标 Mac 的已授权系统用户；是否可连接由屏幕共享/远程管理权限决定 | 重点支持，系统客户端负责认证；不用要求另设 VNC 共享口令 |
| Apple Account（原 Apple ID） | Apple 系统客户端提供的账号连接/请求共享流程 | 单独入口或后续范围，不能把 Apple Account 密码当作远端 Mac 的 VNC 密码 |
| VNC 共享密码 | “VNC viewers may control screen with password”中的独立口令 | 兼容选项，不作为连接 Mac 的首选，更不能擅自开启 |

Apple 的屏幕共享说明支持输入主机名或 Apple Account，并在需要时输入用户名密码；共享设置可以按系统用户/组授予访问，也提供独立的 VNC 密码开关。两种入口不能因此视为同一个自动登录 API。[A1][A2][A3]

第三方客户端并非都只支持共享口令。noVNC、LibVNCClient、TigerVNC 均有 Apple ARD/DH security type 30 的账号认证实现；但当前 macOS 的认证选择与加密可能因版本和目录绑定不同而变化。实现 type 30 不等于支持 Apple Account，也不等于具备 Apple 高性能屏幕共享。源码核查不替代目标 macOS 真机握手测试。[A6][R1]

## 建议的第一版交互

### 入口

- 现有 Mac 主机的右键菜单及详情区增加“打开远程桌面”。文件、终端、监控继续使用同一主机身份。
- 不给每个 SSH 标签常驻一个大的远程桌面面板；没有实际会话时不占工作区。
- 第一次连接只补充网络方式、屏幕共享地址/端口；SSH 连接可复用现有主机及跳板配置。

### 网络

- 已有可达 SSH 时优先提供“经 SSH 安全连接”；复用 SSH 配置和 known_hosts，但桌面隧道与交互终端的进程生命周期独立。
- Farport 本机仅监听 `127.0.0.1` 的临时端口，转发到目标 Mac 的屏幕共享 TCP 端口，默认 5900；不开放本机局域网监听。[A3]
- 若 SSH 终点就是目标 Mac，转发目标可以是它的 `127.0.0.1:5900`；若 SSH 仅是跳板，目标应是跳板可达的 Mac 地址。界面要显示完整目标关系，不能把两种情况静默混用。
- 可信局域网/VPN 可显式选择直连；仅凭私网地址不能自动认定网络可信。
- 系统客户端调用可用无密码的 `vnc://127.0.0.1:<port>` 作为验证原型，但自定义端口、正确账号对话框、Keychain 的目标身份及多隧道并存必须实机验证后再交付。不得把密码放进 URL、命令行或日志。

### 认证与状态

- 第一版不另写一套模拟 Apple 登录框；屏幕共享账号由系统客户端采集，Farport 不代输/缓存密码，不默认把 SSH 账号等同于屏幕共享账号。
- Farport 只承诺自己可观察的状态：“正在建立隧道”“隧道就绪”“已打开系统屏幕共享”“通道断开”。启动客户端不能被标成“桌面已登录”。
- 不依靠 UI 自动化或读取系统客户端的私人 Keychain 条目确认登录。对外部客户端是否关闭单个连接，如无可靠公开事件，首期保留可见的显式“断开隧道”，不能把系统客户端退出或存在等同于单个连接状态。
- 关闭终端标签不关闭远程桌面隧道；Farport 退出或用户断开隧道会影响隧道中的桌面，要预先提示。用户经直连打开的系统桌面由系统客户端管理。

### 错误处理

连接失败至少区分 SSH 认证/指纹、网络不可达、目标端口不可达、屏幕共享账号未获授权、用户拒绝共享。外部系统客户端产生的认证错误由其显示，Farport 不伪造细分原因。

目标未开启服务时给出设置指引，不能自动执行提权开启命令。Screen Sharing 与 Remote Management 不能同时开启；已使用 Remote Management 的机器不得为适配 Farport 自动关闭原服务。[A2]

## 标准与高性能模式必须分开

Apple 高性能模式要求支持的 Apple Silicon/macOS 组合、低延迟高带宽，且两端可通过 UDP 5900、5901、5902 通信；支持音频、虚拟显示器等能力。官方给出的单个 4K 显示器带宽要求为 75 Mb/s。它并不是“普通 VNC 多开一个高画质开关”。[A4][A5]

因此第一版的普通 TCP SSH 转发只按标准屏幕共享设计和验收，不承诺高性能模式。已有可信直连/VPN 时，由系统客户端提供可用的模式选择，不能通过“自动降级”悄悄绕过用户选择的 SSH 安全通道。[A4][A5；工程推论]

高性能连接还可能使远端物理显示器变黑、影响当地用户继续操作，系统客户端应保留自己的提示与选择，不能只把它宣传成无感查看。[A4]

## 若用户要求必须内嵌

内嵌可以进入验证原型，但需要重新估算范围：帧缓冲绘制、键鼠焦点、中文输入、Command/Option、Retina 缩放、多显示器、剪贴板授权、断线恢复以及生命周期都由 Farport 承担。

- noVNC 有账号认证和协议测试，可用作候选；但要维护 WebView、WebSocket→TCP 适配与页面资源权限。不能因为选了 noVNC 就承诺 Apple 原生性能和体验。
- 原生 C/C++ 候选有 LibVNCClient、TigerVNC，但加密构建条件与许可证需要单独评估，不能直接作为 MIT 产品的随意替换组件。
- 使用第三方 ARD/DH 认证时，凭证加密不代表整条桌面连接全程加密；仍需安全传输设计。

以上实现与许可事实的固定源码证据见 [认证侧证据](2026-10-19-mac-vnc-auth-evidence.md)。本轮未选择库，也未写内嵌代码。[R1]

## 必须通过的验收

1. 关闭传统 VNC 共享口令，仅授权指定 Mac 用户，仍可用其系统账号连接。
2. 错误密码、未授权用户、目标未开服务：错误有可理解的归属，不自动放宽权限。
3. 普通用户与管理员、当前桌面已登录/锁定、另一用户已登录：观察与控制行为符合目标系统策略。不能用“屏幕共享”承诺绕过 FileVault 开机解锁。
4. 中文输入、Command/Option/快捷键、多显示器、缩放、剪贴板开关；不无意把快捷键或剪贴板发到错误主机。
5. 同时连接两台 Mac，经不同 SSH 跳板、本地临时端口冲突、网络切换、休眠唤醒、关闭终端标签：不串会话，不错误复用账号。
6. 多次连接/取消/关闭，隧道进程与本地端口及时释放，不把关闭一个屏幕会话扩大为关闭系统 Screen Sharing 的所有连接。
7. 直连标准、SSH 标准分别验证；高性能只在满足官方要求的直连/VPN环境验证，不用普通 VNC 测试代替。
8. 最终发行包安装验收，不以命令行原型成功代替。当前已有发行稳定性问题应保持优先级，不能因新增远程桌面掩盖。

## 已收敛的首期范围

- 用户接受推荐方案，因此首期由 Farport 一键打开系统 Screen Sharing，不内嵌桌面渲染。
- 首期“原生账号”按远端 Mac 已授权系统用户的用户名密码验收；这是一项明确的产品范围选择，不把它解释为 Apple Account/iCloud 请求共享已经支持。
- 优先解决自己的远程 Mac 的访问，不扩展为客服式远程协助。已有 SSH 时优先安全隧道，可信直连/VPN 必须显式选择。
- 标准屏幕共享是首期承诺；Apple Account、内嵌渲染及高性能模式不作为首期交付条件。
- 公开调用的自定义端口、目标身份隔离、系统认证和隧道释放仍需真机原型验证；未达标前不得发布为已支持。
